# 0005. 오류 보고: Sentry (서버 측만)

| 항목 | 내용 |
| --- | --- |
| 상태 | 채택 |
| 날짜 | 2026-10-26 |
| 관련 요구사항 | D-03, D-05, D-10 |

## 배경

수집 소스는 비공식 엔드포인트라 예고 없이 스키마가 바뀐다(ADR 0001). 검증에 실패한 응답을 나중에 보고 원인을 찾을 수 있어야 한다. 원본 응답을 매번 DB에 쌓는 것은 용량 대비 쓸모가 적어, 실패한 경우만 로그 관리 도구로 보내기로 했다(인터뷰, 2026-10-26). 비용 0원 지향(C-02).

## 고려한 대안

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. Sentry 무료 Developer 플랜 | 오류 묶음·알림·검색, Next.js SDK, 0원 | 서비스 하나 추가, 월 오류 이벤트 한도 |
| B. DB(`collection_run`)에 응답 일부 저장 | 추가 서비스 없음 | 알림·검색 없음, 보고 싶을 때 SQL로 찾아야 함 |
| C. Vercel 런타임 로그만 | 설정 없음 | Hobby 보관 기간이 짧고 묶음·알림 없음 |

## 결정

**A를 채택한다.** `@sentry/nextjs`를 서버(Node.js 런타임)에서만 초기화한다.

- `SENTRY_DSN`이 없으면 초기화하지 않는다(로컬·CI는 기본적으로 보내지 않음).
- 수집 소스 오류는 `captureException`으로 보내고, 검증 실패는 zod 오류와 응답 앞 2 KB를 함께 첨부한다.
- `collection_run.results`에는 상태 요약만 남긴다.
- 클라이언트 SDK, 성능 추적, 소스맵 업로드는 쓰지 않는다(필요해지면 이 ADR을 갱신).

## 결과

- 이점: 스키마 변경을 알림으로 바로 알고, 실패 응답을 그대로 볼 수 있다.
- 감수하는 리스크와 대응:
  - 같은 오류가 15분마다 반복되면 이벤트 한도를 쓴다 → Sentry가 같은 오류를 한 이슈로 묶는다. 한도에 가까워지면 샘플링을 넣는다.
  - 응답 일부가 외부 서비스로 나간다 → 공개 게임 데이터뿐이고 비밀정보가 없다.
- 후속 작업: D-10 구현, `.env.example`에 `SENTRY_DSN` 추가, Sentry 프로젝트 생성(사용자).
