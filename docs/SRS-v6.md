# 헬다이버즈2 대시보드 — SRS v6 (화면 자동 갱신)

| 항목 | 내용 |
| --- | --- |
| 문서 버전 | v6.0 (2026-10-29) |
| 상태 | 사용자 결정 반영 (2026-10-29) |
| 범위 | 열어 둔 탭이 15분 수집 주기에 맞춰 스스로 최신 데이터를 받는다 |
| 입력 | [SRS v2](SRS-v2.md) F-05-1·Q-02·Q-05, [SRS v4](SRS-v4.md) §3 캐시, PR #16(수집 직후 예열) |

## 1. 문제

수집은 Supabase Cron이 매시 00·15·30·45분(UTC 15분 경계)에 돌리고, 끝나면 캐시 태그를 무효화하고 `/`·`/news`·`/stats`를 예열한다(PR #16). 서버 쪽 페이지는 수집 직후 새것이 된다.

하지만 이미 열려 있는 탭은 렌더 시각의 데이터에 고정된다. 브라우저에서 도는 것은 지연 배지의 1분 타이머뿐이라, 탭을 켜 두면 수치는 그대로이고 30분이 지나면 수집이 정상이어도 "데이터 지연" 배지가 뜬다. 최신 데이터를 보려면 새로고침해야 한다.

## 2. 요구사항

| ID | 내용 | 우선순위 |
| --- | --- | --- |
| A-01 | 수집 슬롯 + 2분(매시 02·17·32·47분, 브라우저 시계 기준)이 지났는데 화면의 수집 시각이 이번 슬롯보다 이르면, 새 데이터가 올 때까지 1분마다 페이지 데이터를 다시 받는다. 전체 새로고침이 아니라 `router.refresh()`로 받아 스크롤·펼침 상태를 유지한다. 홈·뉴스·통계 모두 | M |
| A-02 | 탭이 숨겨져 있는 동안은 받지 않는다. 다시 보일 때 바로 한 번 판단해, 뒤처져 있으면 받는다 (함수 호출·대역폭 절약, Q-05) | M |
| A-04 | 수집 직후 캐시 태그를 바로 만료한다(`revalidateTag(tag, { expire: 0 })`). 예열 요청이 새 화면을 끝까지 렌더하고, 방문자는 첫 요청부터 새 HTML을 받는다 | M |
| A-03 | 갱신 뒤 LAST UPDATE 시각과 지연 배지가 새 수집 기준으로 바뀐다(F-05-1). 갱신해도 마지막 수집이 30분 넘게 지났으면 배지는 그대로 뜬다 | M |

## 3. 결정 (2026-10-29)

| 질문 | 결정 |
| --- | --- |
| 갱신 시각 | 슬롯 + 2분. 수집(약 10초) + 예열 대기 3초 + 렌더가 끝난 뒤이고, 브라우저 시계가 1분쯤 틀려도 새 데이터를 받는다 |
| 기준 시계 | 브라우저 시계의 UTC 15분 경계(cron과 같은 경계)와 화면에 실린 수집 시각을 비교한다 |
| 받았는데 아직 옛 데이터일 때 | 1분 뒤 다시 받는다. 로컬 `next start` 실측: 예열은 HTML만 데우고, `router.refresh()`가 쓰는 RSC 응답은 수집 뒤 첫 요청에 옛것을 주며 재생성을 일으킨다. 그다음 요청부터 새것이다. RSC 주소의 `_rsc` 값은 Next 내부 해시라 서버에서 같이 예열하지 않는다 |
| 수집이 멈췄을 때 | 열린 탭마다 1분에 한 번 받는다(캐시 HIT라 함수 호출 없음). 사용량에 문제가 보이면 횟수 상한을 둔다 |
| 적용 위치 | 모든 화면 머리에 있는 지연 배지(`StaleBadge`)의 1분 판단에 붙인다. 수집 시각을 이미 갖고 있어서 따로 컴포넌트를 두지 않는다 |
| 캐시 무효화 (A-04, 2026-10-29 추가) | `"max"`는 페이지와 캐시된 읽기 함수가 각각 한 번씩 옛것을 더 줘서, 예열 뒤에도 몇 번의 요청 동안 옛 화면이 나왔다(로컬 실측). 외부에서 부르는 라우트에는 `{ expire: 0 }`이 Next 문서의 권장 방식이다 |
| 문서 | 이 문서(SRS v6)와 CHECKLIST P4 "자동 갱신" 절. 현재 단계는 P4 유지 |
